# TawkType review — September 11, 2026

**TawkType is a credible personal-use prototype, but its privacy and delivery guarantees are stronger than its implementation.** I would spend the next release on preserving the user’s words, preventing unintended actions, and making privacy controls truthful. More rewriting features would currently amplify weaknesses in the delivery path.

I reviewed HEAD `6be98ea`: the handoff first, architecture, README, branding, implementation across all five projects, tests, packaging, and recent commit reasoning. I checked several dependency assumptions against primary documentation and reproduced the filler-regex failures in memory. I did not launch the app, run the test suite, make API calls, or modify files during the review. Hardware-dependent findings below are identified accordingly.

Source references below use repository-relative paths and line numbers from the reviewed commit.

## Engineering, correctness, and safety findings

### 1. [P1] Turning history off does not stop transcripts being written to disk

Both engines log the full recognized text:

- `src/TawkType.Transcription/ParakeetTranscriber.cs:64`
- `src/TawkType.Transcription/WhisperTranscriber.cs:85`

`src/TawkType.App/App.xaml.cs:83` enables Debug logging, and the file logger retains both the current log and a rotated `.1` file.

Consequently, disabling or clearing history leaves another plaintext transcript archive. Even dictations that subsequently fail delivery can be there. The handoff’s description of metadata-only logging is wrong.

**Remove transcript bodies from normal logging entirely.** An opt-in diagnostic mode should require a separate, explicit choice. Audit exception logging too: provider exceptions should not automatically become permanent diagnostic records without checking what they contain.

### 2. [P1] History retention and deletion are not trustworthy

`src/TawkType.Core/History/DictationHistoryStore.cs:90` decides whether to compact using the in-memory count. But loading trims that count without rewriting the file at line 171.

A concrete sequence: retain 200 entries, dictate 20 times, restart, repeat. Each restart reduces memory back to 200; the app never exceeds its 250-entry compaction threshold during a session. **The disk file can grow indefinitely while the UI consistently shows 200 entries.**

Other problems in the same store:

- `Clear()` clears memory before attempting deletion and swallows deletion failures. The UI looks empty even when the file survives and will reload next launch.
- Compaction overwrites the existing file directly. A crash during compaction can destroy previously valid history.
- A genuinely torn final line without a newline will absorb the next appended record. The existing torn-line test explicitly adds a newline, missing this case.
- Persistent append failures also prevent the in-memory trimming code from running.

Retention must describe what remains **on disk**, and deletion needs a success/failure result. Use atomic replacement for compaction.

There is also a conditional resurrection problem: `src/TawkType.App/Services/LegacyMigration.cs:66` imports an old history file whenever the destination is absent. If an older copy was previously skipped because a current file existed, clearing current history can make that old copy eligible for import on the next launch. Migration needs a completion marker, not permanent “missing file means migrate” behavior.

### 3. [P1] Text injection can submit messages or execute commands

`src/TawkType.Windows/Injection/TextInjectors.cs:25` converts every newline into a real Return keypress. The LLM explicitly produces paragraphs and lists.

In an Enter-to-send chat box, a short multiline rewrite can send its first paragraph immediately. In a terminal, it can execute the first line. Auto mode chooses by character count, so the same kind of content can behave differently below and above 400 characters.

Separately, `src/TawkType.Windows/Injection/NativeInput.cs:50` waits 750 ms for modifiers, then injects anyway. Holding Alt, Shift, or Ctrl longer than that defeats the purpose of waiting. Microsoft explicitly warns that existing keyboard state can interfere with `SendInput`. [SendInput documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

**Treat delivery as an application-sensitive operation.** Do not turn unreviewed newlines into submission keys. On unresolved modifiers or an unsafe target, retain the result for explicit delivery. Pasting multiline text is not universally safe in terminals either.

### 4. [P1] The focus probe does not protect the actual delivery destination

`src/TawkType.Core/Pipeline/DictationEngine.cs:133` schedules a probe at key-down, then uses that old verdict after transcription and rewriting. No target identity is checked immediately before injection.

Dictate in Notepad, switch to a chat window during processing, and the Notepad verdict authorizes input into the chat window. The asynchronous probe does not even guarantee that it observes focus at the exact moment of key-down.

Keep the early probe for responsiveness, but capture a target identity and revalidate before delivery. If the user moved elsewhere, hold the result instead of guessing or stealing focus back. Window identity alone will not distinguish two fields or browser tabs, so document the limits.

The elevation detector is also wrong: `src/TawkType.Windows/Input/UiaFocusProbe.cs:169` treats successful `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` as “not elevated.” That permission is not an integrity-level test. Inspect process tokens and compare integrity levels. [Microsoft’s integrity-level guidance](https://devblogs.microsoft.com/oldnewthing/20221017-00/?p=107291).

Finally, the probe never checks `IsPassword`. Sensitive fields need an explicit policy before either cloud cleanup or history recording, not merely a decision about whether typing might work.

### 5. [P1] Recovery happens after the operation most likely to fail

`src/TawkType.Core/Pipeline/DictationEngine.cs:216` injects before raising `Completed`; `src/TawkType.App/App.xaml.cs:290` records history only from that completion event.

If `SendInput` partially fails or clipboard access fails, recognized text is absent from user-facing history. “Nothing is lost” is therefore false precisely when recovery matters most. Successful `SendInput` also does not establish that the application inserted the intended text.

Introduce a result before delivery, with separate delivery status: pending, attempted, copied, failed, or possibly partial. Keep an in-memory recovery buffer even when persistent history is disabled. Do not blindly retry partial typing—it can duplicate text.

### 6. [P1] Clipboard handling can destroy unrelated user data

`src/TawkType.Windows/Injection/TextInjectors.cs:65` already acknowledges loss of images and files. That is not an acceptable invisible side effect of Auto mode.

There are additional races:

- A fixed 200 ms delay does not establish that the target consumed the clipboard.
- If the user copies something during that delay, restoration overwrites their new clipboard.
- Restoration is skipped if injection throws.
- When previous text is absent, the transcript remains on the clipboard.

Restore only if the clipboard still contains your temporary value, using its sequence number. Preserve supported formats, and make any unavoidable destructive behavior explicit.

`src/TawkType.Windows/Injection/NativeClipboard.cs:94` also opens with a null owner before calling `EmptyClipboard` and `SetClipboardData`. Microsoft documents this sequence as causing `SetClipboardData` to fail. This is a documented contract violation; I have not reproduced its behavior on your Windows build. Use a real owner window and test the native path. Allocation failure handling also needs checking before writing through `GlobalLock`’s returned pointer. [SetClipboardData documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setclipboarddata).

Clipboard history/cloud-sync exclusion formats are absent. Depending on Windows settings, temporary dictation clipboard content can be retained or synchronized outside TawkType. Use Windows’ exclusion mechanisms for temporary paste content; these cannot control arbitrary third-party clipboard managers. [Clipboard formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats).

### 7. [P1] Stopping the engine does not stop an active dictation

`src/TawkType.Core/Pipeline/DictationEngine.cs:93` only disconnects the hotkey and events. It neither stops capture nor cancels or awaits the processing task. That task is discarded at line 169, and no cancellation token reaches transcription, cleanup, or injection.

Shutdown then disposes services while processing can still be using them. A stopped engine can continue toward injection. There is no operation identifier to distinguish stale work, no recording-duration ceiling, and no session-lock/suspend handling.

Give each dictation an owned task, cancellation source, settings snapshot, and terminal outcome. Shutdown should first reject new work, stop recording, cancel pending delivery, await bounded cleanup, then dispose dependencies.

Other state-machine fragility:

- State-change subscribers execute while `_gate` is held.
- Exceptions from subscribers can derail transitions; an exception in the failure-notification path can leave the engine stranded.
- Hold duration is calculated when the worker runs, rather than at release. Scheduling delays can turn an accidental tap into an accepted recording.
- The tray test action can end an existing dictation even if its own `BeginDictation()` was ignored.

### 8. [P1] Hotkey suppression leaks repeated keypresses

In `src/TawkType.Windows/Input/PushToTalkHotkey.cs:102`, repeat events return without setting `Handled`. With suppression enabled, the initial trigger is swallowed but subsequent repeats reach the application. A held letter can type repeatedly; a held shortcut can repeatedly invoke its application command.

Releasing a modifier first also loses suppression tracking for the trigger’s eventual release. Swapping hotkey settings while a combination is held can make the old release unrecognizable.

Extract a pure event reducer that tracks both an active gesture and which physical keys it has swallowed. Preserve those decisions until their matching releases.

Two smaller concrete issues:

- `src/TawkType.Core/Input/Hotkey.cs:71` splits on `+`, but `VirtualKey.Describe` emits `Numpad +`. That recorded key cannot round-trip through settings.
- `src/TawkType.App/Views/HotkeyBox.xaml.cs:85` handles WPF events without suspending the global hook. Recording the existing hotkey can trigger dictation; an existing suppressed trigger may never reach the picker.

### 9. [P1] Audio startup and shutdown assume guarantees NAudio does not provide

`src/TawkType.Windows/Audio/WaveInAudioCapture.cs:55` assigns `_waveIn` only after `StartRecording()` succeeds. If startup throws, the created object and any partially acquired resources are not disposed.

At line 79, stopping disables capture and unsubscribes before stopping the device. Any pending final samples are discarded. How audible this is needs a boundary test with real capture.

More seriously, the comment claiming `StopRecording` joins the capture thread is false for NAudio 2.2.1: it changes state, stops/resets the device, signals an event, and returns. TawkType immediately disposes afterward. The adapter should coordinate with `RecordingStopped`, which also carries recording-thread failures; currently it never subscribes. [Pinned NAudio source](https://raw.githubusercontent.com/naudio/NAudio/v2.2.1/NAudio.WinMM/WaveInEvent.cs).

Also, `_audio.Start()` runs synchronously inside the keyboard-hook callback. Device opening can block. Whisper’s initial `WhisperFactory.FromPath` can likewise run synchronously on the UI thread during startup, because an uncontended semaphore await does not yield. That UI thread owns the hook. Windows can silently remove timed-out hooks. See `src/TawkType.Transcription/WhisperTranscriber.cs:138` and [Windows hook documentation](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc).

### 10. [P1] The default cleaner damages legitimate multilingual speech

`src/TawkType.Core/Text/BasicTextCleaner.cs:50` removes English-looking fillers regardless of language. I reproduced:

| Input | After filler removal/spacing |
|---|---|
| `Wir treffen uns um acht.` | `Wir treffen uns acht.` |
| `Er kommt morgen.` | `kommt morgen.` |
| `The ER is open.` | `The is open.` |

This is a significant correctness defect for an app advertising multilingual support. The “ER” case also demonstrates that merely restricting it to English is insufficient.

Cleanup also flattens all line breaks and capitalizes the first character unconditionally. Disabling filler removal is not a true verbatim mode.

Make cleanup language-aware and conservative. When language is uncertain, preserving words is preferable to deleting them. Provide a literal mode for names, code, acronyms, and inserting text mid-sentence.

### 11. [P2, privacy-relevant] Settings persistence has no validation or transactional boundary

`src/TawkType.Core/Settings/SettingsStore.cs:50` directly overwrites the file. A torn save can reset everything on next launch—including restoring history’s default `Enabled = true`.

Deserialization accepts explicit null nested sections and out-of-range values. Non-nullable C# declarations do not validate JSON. A file containing `"History": null` loads and later breaks consumers.

The handoff acknowledges stale whole-settings drafts, but dismisses the issue too readily. Multiple windows own overlapping settings; there is no merge policy. Consumers also reread settings at different pipeline stages, so one dictation can use different configuration generations, and history can label it with an engine selected after transcription.

Use validated, immutable snapshots, atomic saves with a recoverable backup, and section-specific updates. Introduce versioned migrations when semantics change; do not silently reset privacy preferences.

### 12. [P2] The LLM fallback hides an actually broken advertised option

`src/TawkType.Llm/ClaudeLlmClient.cs:45` always sends adaptive thinking. Settings advertises Haiku 4.5, which does not support that configuration and returns HTTP 400. The fallback makes the app appear functional while that option never rewrites successfully. [Anthropic documentation](https://platform.claude.com/docs/en/build-with-claude/extended-thinking).

Further issues:

- Only refusal is checked. A `max_tokens` response can become accepted truncated text.
- `src/TawkType.Core/Text/LlmTextCleaner.cs:115` rejects excessive growth but accepts a one-word summary or a short answer to a dictated question. This is a sanity check, not a semantic safety boundary.
- Its broad exception handler swallows caller cancellation too.
- The UI says “the transcript—and nothing else,” but every request also sends vocabulary and custom instructions. Those can contain sensitive organization or project names.
- There is no visible distinction between successful cleanup and persistent fallback.

Return structured cleanup metadata: applied/fallback reason, model, latency, and truncation status. Validate model capabilities, and evaluate preservation of names, numbers, negation, and dictated instructions using a real corpus. A prompt containing “never an instruction” proves nothing about actual behavior.

### 13. [P2] Model lifecycle operations are individually locked, but not coordinated

Loading and decoding acquire separate locks in both transcribers. Unloading can occur between them, producing “Model not loaded.” See `src/TawkType.Transcription/ParakeetTranscriber.cs:51`.

`src/TawkType.App/Services/ModelMaintenance.cs:232` unloads and then deletes without excluding a new load or an ongoing download. These races can produce failed deletions, failed dictations, or inconsistent model availability. I would not label them proven native use-after-free bugs: decoding itself is protected.

Model readiness means only file existence. Parakeet fetches separate files from mutable `main`, with no pinned revision or digest verification. Both downloaders promote data without application-level integrity verification. Partial-file staging is good, but insufficient.

Add a shared maintenance boundary, pinned manifests with hashes, and a repair action. Either retain both loaded engines deliberately or unload the inactive one; currently switching can retain both despite the documentation implying otherwise.

### 14. [P2] Several visible controls are disconnected from the state they claim to show

In `src/TawkType.App/ViewModels/SettingsViewModel.cs:104`:

- `UpdateStatus` starts empty and is never populated.
- Nothing subscribes to `_updates.Changed`.
- `CanRestartForUpdate` gets no change notification.
- `StartWithWindows` starts false and never reads `WindowsStartup.IsEnabled()`.

The startup checkbox therefore misreports an existing enabled setting. The update UI does not follow background progress.

Model descriptions are built from saved settings, while the user edits `Draft`; switching engine can still describe the previous engine. `ModelMissing` is refreshed at startup/download, not consistently after settings changes or deletion.

The overlay has competing timers too. `ShowError` schedules three seconds, but the following Idle event replaces it with 450 ms. Warm-up completion can schedule an idle presentation during active dictation, and warm-up failure does not clear model-busy state. See `src/TawkType.App/ViewModels/OverlayViewModel.cs:145`.

Use one presentation state derived from pipeline state, model readiness, and notices with explicit precedence. Recording indication must not be accidentally replaced by “Hold Right Ctrl.”

### 15. [P2] Distribution needs testing away from the developer machine

`build/pack.ps1:75` does not specify a runtime prerequisite, although the README promises the installer will fetch the Desktop Runtime. Velopack documents prerequisite bootstrapping through `--framework`; verify the generated installer on a clean machine and declare `net8.0-x64-desktop` explicitly. I did not test the installer. [Velopack bootstrapping](https://docs.velopack.io/packaging/bootstrapping).

The build installs an unpinned global `vpk`, while the app pins its SDK. Pin the toolchain together. The only checked-in workflow runs on release tags/manual dispatch, so ordinary changes have no automatic build/test gate.

There is also an approaching maintenance deadline: .NET 8 support ends **November 10, 2026**. Plan the runtime upgrade now, including the tray-library compatibility problem. [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core).

## Product priorities

For product work, I would rank the missing capabilities this way. These are priorities for this codebase, not a checklist copied from a competitor.

| Rank | Capability | What I would build here |
|---|---|---|
| 1 | **Reliable recovery and controlled delivery** | In-memory last result independent of history, delivery failure status, explicit copy/retry, focus-change detection, safe multiline behavior. |
| 2 | **A real privacy mode** | No transcript logging, a clear retention choice during onboarding, per-entry deletion, visible deletion failures, temporary no-history/no-cloud mode, sensitive-field protection. Consider DPAPI-encrypted history after getting retention semantics right. |
| 3 | **First-run setup that ends with a successful dictation** | Recommend one model, explain its download, select/test microphone, record/test hotkey, and dictate into an app-owned practice field. Show readiness and actionable permission/device errors. |
| 4 | **Cancel, pause, and toggle-to-talk** | Escape to cancel active work, a global pause control, optional press-on/press-off mode, recording time limit, stop on session lock. Holding a chord is unsuitable for some users and long dictation. |
| 5 | **Useful local vocabulary and formatting** | Exact replacements and a personal dictionary that work without Claude; recognition hints where supported; literal mode; deliberately scoped spoken punctuation/paragraph commands. |
| 6 | **Microphone resilience** | Stable device identity, refreshable device list, hot-unplug handling, silence/clipping feedback, and an explicit decision when the selected microphone disappears. Silent fallback to another microphone is surprising. |
| 7 | **Accessible feedback** | Optional start/stop/error sounds, keyboard-accessible alternatives to the nonactivating overlay, labeled controls, high-contrast support, and usable layouts under large text scaling. |
| 8 | **Per-app profiles** | Start with delivery mode, newline handling, privacy, and literal/prose mode. Tone presets come later. These settings should use the captured destination, not whichever app happens to be foreground after processing. |

I would **not build yet**: live partial injection, streaming LLM output into arbitrary applications, selected-text command mode, automatic learning from user edits, or a broad local-LLM/backend catalogue. They introduce revision, focus, privacy, and lifetime problems before the current ones are controlled. A partial transcript in the overlay is a safer later experiment than streaming it into another application.

I also would not replace WPF, add an account, or introduce a database simply to fix these defects. JSONL can support this scale if its durability and retention behavior are corrected. The stack is not the main problem.

## Testing priorities

The testing investment should follow failure cost.

| Test investment | What would actually catch the problems |
|---|---|
| **Deterministic pipeline tests** | Gate each stage with task-completion sources. Stop during recording/transcription/cleanup; change focus/settings; throw during injection; assert no late delivery and a recoverable result. Replace timing guesses with an injectable clock. |
| **Pure hotkey event-sequence tests** | Initial press, repeats, modifier-first release, settings changes mid-hold, suppression pairing, and every supported key’s parse/print round trip. No real keyboard hook is required for most of this. |
| **Filesystem failure tests** | Repeated restart cycles under the retention threshold; torn final line without newline; failed deletion; failed compaction; corrupt/null settings; legacy files remaining after migration. Assert disk contents, not just `Recent.Count`. |
| **Small Windows integration harness** | Own test edit controls and a message-only clipboard owner. Exercise Unicode, surrogate pairs, multiline text, clipboard contention/formats, focus switching, and elevated targets. Assert received text and actions, not merely successful API return values. |
| **Audio adapter tests plus hardware smoke tests** | Fake callbacks arriving during stop, startup exceptions, `RecordingStopped` failures, and final-buffer preservation. Separately test unplugging a USB mic, unavailable mic access, Bluetooth changes, and suspend/resume. |
| **WPF binding and presentation tests** | Open Settings with startup already enabled; advance updater state; change draft engine; issue Error→Idle; complete warm-up during Listening. Catch binding errors and verify visible state. |
| **Speech/cleanup evaluation corpus** | Short clips, silence/noise, accents, German filler collisions, names, punctuation, numbers, code, and self-corrections. Measure meaning-changing errors and release-to-delivery p50/p95, not just WER or best-of-five inference time. |
| **Installed-build smoke test** | Fresh standard-user Windows environment without developer tooling; install, download, dictate, update, restart, uninstall/reinstall, and verify data handling. |

The existing tests are useful, but their names sometimes overstate what they establish. `Copies_instead_when_the_target_is_elevated` supplies an already-elevated fake verdict; it does not test elevation detection. The history trimming test checks the reopened in-memory list rather than retained disk records. The prompt test checks wording rather than rewrite behavior. `FakeSettings.Changed` does nothing, so it cannot expose hot-reload defects.

I would not spend effort on pixel-perfect screenshot tests of every theme, mocking every P/Invoke, or exhaustive automation across dozens of third-party editors. A compact manual matrix—Notepad, a browser input, rich editor, chat composer, terminal, elevated app, and password field—will provide more value. Run that matrix whenever injection or focus logic changes.

## Broader observations

- **The documentation contains unsafe certainty.** “Nothing is lost,” “never hallucinates,” “reliable everywhere,” and “the transcript—and nothing else” should become narrower claims backed by tests. Several handoff gotchas now contradict newer code.
- **Swallowing every UI exception is not recovery.** `src/TawkType.App/App.xaml.cs:94` marks every dispatcher exception handled. Expected failures should be handled locally with visible outcomes; unexpected ones should leave the app in a known stopped state rather than silently continuing.
- **The UI currently conceals degraded operation.** A failed rewrite, history-write failure, vanished microphone, or stale update status can look like success. Make failures observable without recording the user’s words.
- **The “time saved” statistic is an estimate with a favorable bias.** It excludes processing/correction time, clips negative savings to zero, and derives totals from retained history. Label it accordingly; it is not evidence of actual productivity.
- **Public positioning is unresolved.** The README invites installation and source execution, then says users have no permission to use the software. Clarify the intended permission model. Code signing and accurate installer instructions matter more for external adoption than further icon polish.

My release priority would be: remove transcript logging; fix retention/deletion; prevent unintended Return/modifier actions; preserve failed-delivery results; then repair capture/hotkey lifetime and add the tests that exercise those contracts. Those changes would make the existing product substantially more trustworthy.
